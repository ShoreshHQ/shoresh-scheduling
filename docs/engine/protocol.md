# The week engine's protocol, rule by rule

Every rule `c/shoreshEngine` applies when it builds a week, in plain words, one line each: the
protocol step it belongs to (Greg's nine steps, wiki `projects/shoresh-sf-engine-care-plan.md`),
the file it lives in, and the test that covers it. Paths are under
`force-app/main/default/lwc/shoreshEngine/`; tests under its `__tests__/`.

- **Gap** in the Test column: no test pins this rule today.
- **To change in a later PR**: the care plan changes this rule; it is written here as it is now.

This list describes the engine as it stands after PR 4a of the care plan (the step 8 search,
rules 8.10–8.18, and early-week goals as the first days of the run, 3.12 and 9.5). PR 1 moved code into
files by step and changed no behaviour (600 random camps build byte for byte the same); PR 3 made
never-blank bend only preferences, says a blank setup field taken as 1, and counts early-week
goals from the week's real first day (rules 1.5, 1.6, 1.10, 3.1, 3.12, 7.1–7.3, 7.8, 9.5, 9.6).
The follow-up after the care plan adds moves between days for weekly minimums (8.24–8.28), and minimums first as a last resort (8.29–8.32, Greg 2026-10-26).

| 8. Search, part 2 (8.10–8.18)     | `weekSearch.js`                       | sixth (after step 7)                                                                |
| 8. Moves between days (8.24–8.32) | `weekAcross.js`, from `weekSearch.js` | after 8.18, before the MIN_COST days again; the last resort (8.29–8.32) after those |

Note the order: the desktop's three repairs (step 8) run **before** never-blank (step 7), as on
the desktop; never-blank fills what they could not; then step 8's exact search (PR 4a,
`weekSearch.js`) takes every cell still Open and fills it or proves it can't be filled.

## The odd-camp library and the settled rules

`__tests__/oddCamps.test.js` builds every camp in `__tests__/data/oddCamps.js` (25 synthetic
camps, each with a line saying what makes it odd) and holds it to the settled rules, checked by
`__tests__/data/settledRules.js` without the engine's code:

- **Hard limits:** the engine never bends who an activity is for, once a day, groups at once,
  groups that fit, or same division only (no flag naming one on a cell it placed).
- **Same input, same output:** built twice, and from its records in reverse order, byte for byte.

  cells kept), plus every minimum short and every early-week goal short listed with the right
  count (early days: the first days of the week's run), and a blank setup field named.

  a preference, so it never excuses a gap); for small camps an exhaustive search, a day at a
  time (every hard limit is within a day), also proves no week fills more cells within the hard
  limits.

Camps: one group; sixty groups; one activity only; weekend-only week; Sunday-start week; goal by
Sunday; half days; overlapping time blocks; every activity closed one day (a camp-wide event, since
closures are per week); a closed place; scarce places; groups away part of the week; heavy

locks and hand edits; other programs share places; special and replaced days; blank groups at

### Step 8 budget

The two quick whole-day limits read only what never moves, so each day's is worked out once,
pausing between groups, and their work counts against the build's.

The search counts its work in search steps (one cell decided) and cells looked at, never time.
Measured on the 400 differential camps: 99% of whole-day proofs need under 4,000 steps, the
largest 29,000; a fuller arrangement is found in a median of 2,000. So: a region search 2,000
steps, a whole day first 20,000 steps in the order that finds the fills leaving fewest short
(99% of fuller days are found within that), then 60,000 deciding multi-block activities one start
at a time (the order that proves days soonest), then 60,000 fewest options first; 2,000 more after a
fuller day is found to change fewer cells, 5,000 per minimums pass, 3,000 moves tried per group
and activity for the moves between days and 60,000 per build (more found nothing more on the 400
camps), 2,000,000 per build; and at
most 15,000,000 cells looked at per build (about 400,000 a second in Node, so a week built twice
stays well under the 3-minute ceiling in a browser; measured below). Inside one
search it pauses every 200 steps so the screen keeps the tab responsive. The slowest differential
camp takes about 11 s in Node, the 60-group odd camp 1.6 s, the 30-group ordinary camp 1.1 s.

Those limits are per build, and one Generate may build up to four times (the stricter second
build, and both again from the imported week), while the repairs before the search grow with the
number of groups: a made-up 80-group week that can't fit took 232 s in Node. So the whole run also
has a ceiling (`RUN_WORK` in shoreshEngine.js, PR 6): 40,000,000 rule checks plus cells looked at,
over every build. Node does about 1.1 million a second on the largest camps, so that is about
35 s in Node, and 70-105 s in a browser two to three times slower: under the 3-minute ceiling.
Past it the repairs and the search stop and the week is finished as it stands (never-blank still

### What the build is doing now

While it builds, the engine says what it is doing as a code and ids (`progress.js`, `NOW`), one
per step, set just before it pauses; the screen reads the latest when it gets the tab back and
says it in camp words (Generated Schedule's `progressWords.js`). Nothing the build reads, so the
week is the same watched or not.

### CI's sample and the full run

The engine's heaviest tests build seeded camps in a loop. CI's default run (`jest.config.js`)
builds a fixed smaller sample, the first seeds of the same list with the same assertions (desktop
differential 100 of 400, the search's proof check 50 of 150, the properties 100 of 300, one ported
option sweep 25 of 100), so the Jest job stays a few minutes. `npm run test:engine:full`
(`jest.full.config.js`) runs every seed: do so before changing the engine. The numbers above are
from the full run.
